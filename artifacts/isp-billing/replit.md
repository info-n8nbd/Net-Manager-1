# Smart Online ISP - ISP Billing System

## Overview
Multi-company SaaS ISP (Internet Service Provider) billing management system for the Bangladeshi market. Built with Laravel 12 and PHP 8.4. Each registered company (ISP) operates in full data isolation. Super Admin manages all companies.

## Technical Stack
- **Backend:** Laravel 12, PHP 8.4, PostgreSQL
- **Frontend:** AdminLTE 3, Bootstrap 4, jQuery 3.6, Font Awesome 6 (CDN), Flatpickr, DataTables, Select2, SweetAlert2, Chart.js
- **Dev Server:** PHP artisan serve on port 5000 (via start.sh)
- **Auth:** Laravel built-in + spatie/laravel-permission RBAC (13 roles, 112+ permissions + 25 extra from PostSetup)
- **PDF:** barryvdh/laravel-dompdf
- **Excel:** maatwebsite/excel
- **Payment Gateways:** SSLCommerz (Full API), bKash (Tokenized Checkout v1.2.0-beta), Nagad (RSA-encrypted official PG API), Rocket (via SSLCommerz + Webhook)
- **Webhook Auto-Payment:** bKash/Nagad/Rocket webhook endpoints for automatic payment verification with client matching by PPPoE username

## Multi-Company SaaS Architecture
- **Companies table:** Each ISP company registered in `companies` table. Company 1 = Default ISP (created by seeder).
- **TenantAware global scope:** All major models auto-filter by `auth()->user()->company_id`
- **Super Admin:** `company_id = NULL` — bypasses all TenantAware scopes, manages ALL companies
- **Company isolation:** All data (clients, bills, payments, employees, zones, packages, etc.) is strictly isolated per company
- **Company admin creation:** When Super Admin creates a company, admin user auto-created with `user_type='admin'` and correct `company_id`
- **`Company::hasMenuAccess($key)`:** Checks `allowed_menus` JSON for exact key AND child-qualified keys. If `dashboard.total_clients` is in allowed_menus, `dashboard` parent access is granted. Without this, company users get 403 on dashboard.
- **Per-company branding:** Sidebar brand name = `Company.name` (from companies table, not SystemSetting); logo/tagline fetched from company-specific SystemSetting row first, falls back to Company 1's settings if not found.
- **Employee ID per-company:** `employees.employee_id` unique constraint is `(company_id, employee_id)` (migration `2026_03_12_000001`). Each company starts its own EMP-0001 sequence. `Employee::generateEmployeeId()` uses `withoutGlobalScopes()->where('company_id')`.
- **Company admin credentials:** Super Admin can update company admin's name/email/password from Company Edit page (Admin Login Credentials card).
- **New company default data seeding:** `CompanyManagementController::store()` calls `seedCompanyDefaults($companyId)` after company+admin creation. Seeds: 5 payment methods (Cash/bKash/Nagad/Rocket/Bank Transfer), 4 accounts, 3 income heads, 4 expense heads, 4 ticket categories, SMS templates (copied from Company 1), 4 departments, 4 designations. `PostSetup::seedAllCompanyDefaults()` backfills ALL existing companies missing these records — runs on every startup. Idempotent (skip-if-exists logic).
- **Per-company unique codes:** `payment_methods.code` and `sms_templates.code` changed from global unique to compound unique `(code, company_id)` via migrations `2026_03_12_200000` and `2026_03_12_200001`. This allows each company to have their own `cash`, `bkash`, `payment_received` codes independently.

## Payment Method Permission System
- **Table:** `payment_method_perms` (migration `2026_03_12_140242`) — `payment_method_id`, `user_id` (nullable), `role_id` (nullable), `company_id` (nullable)
- **Logic in `User::allowedPaymentMethods()`:**
  1. Admin (`user_type='admin'`) → all active methods (bypasses all restrictions)

  3. Check `payment_method_perms` for user's role_id → if rows found, only those methods

## Installation Charge System (Service Charges)
- **Base Entry Pattern:** When a client is created (via approval or direct), a base `ClientServiceCharge` entry is auto-created with `charge_type='Installation Charge'` and `paid_by=NULL`. This is the "charge record" (the amount owed).
- **Payment Entries:** When someone pays the installation charge, a SEPARATE `ClientServiceCharge` entry is created with `paid_by` set to the collector's user ID. These are the "payment records".
- **Status Calculation:** `$icPaidTotal` = sum of payment entries (whereNotNull paid_by). Status = Free (amount=0), Paid (paid >= amount), Partial (paid > 0 but < amount), Due (no payments).
- **Service Charges Page (`admin/sales/services`):** Shows ONE row per client's installation charge (the base entry). Status badge computed dynamically. Payment sub-records are hidden. Edit form for base entries shows only Amount field (0=Free, >0=Due).
- **Client Profile:** Filters OUT base Installation Charge entries (whereNull paid_by) from the service charges table. Only actual payments shown. Billing summary shows "FREE" badge when installCharge=0.
- **Sync Logic:** `syncInstallationCharge` and `payInstallationCharge` both use `whereNotNull('paid_by')` when summing paid amounts. Guard against duplicate base entries.
- **Pay Button:** Available directly on Service Charges page for installation charges with Due/Partial status.

## Architecture: Package vs Profile (CRITICAL)
- **Package = billing ONLY** — name, price, download/upload speed (display), type, status
- **Profile = MikroTik speed ONLY** — stored in separate `mikrotik_profiles` table
- **No fixed binding** between Package and Profile — any package + any profile combination allowed
- **`mikrotik_profiles` table** — separate table for MikroTik PPP profiles (name, rate_limit, download_speed, upload_speed, speed_unit, local_address, remote_address, source_device, profile_type)
- **`MikrotikProfile` model** — `app/Models/MikrotikProfile.php`
- **Profile management page** — integrated into Package page as a tab (Admin > Config > Package & Profile)
- **Sync from Router** — fetches PPP profiles from all active MikroTik devices into `mikrotik_profiles` table

## OLT SNMP Monitoring Architecture
- **SNMP Tools:** `net-snmp` package installed via Nix (snmpget, snmpwalk, snmpset CLI tools)
- **PHP SNMP:** No php-snmp extension available; uses CLI fallback (shell_exec with `-OQn` flag for numeric OIDs)
- **Namespace:** `app/Services/OLT/` — all SNMP-related services
- **OID Mapping System:**
  - `OIDMapping` — base class with standard MIB-2 OIDs (sysDescr, sysUptime, sysName, ifInOctets, ifOutOctets)
  - `BdcomOIDMapping` — BDCOM enterprise OIDs (EPON), ONU status/power/MAC
  - `VsolOIDMapping` — VSOL enterprise OIDs
  - `HuaweiOIDMapping` — Huawei enterprise OIDs (MA5680T series)
  - `ZteOIDMapping` — ZTE enterprise OIDs (C320/C300 series)
  - `GenericOIDMapping` — Generic/fallback OIDs
  - Factory method: `OIDMapping::forVendor($vendorName)` creates correct vendor mapping
- **SNMPClient (`app/Services/OLT/SNMPClient.php`):**
  - Wraps CLI snmpget/snmpwalk commands with typed error classification
  - Error types: timeout, unreachable, auth_error, oid_not_found, unknown
  - SNMPv2c with community string authentication
  - Methods: `get()`, `walk()`, `getSystemInfo()`, `testConnection()`
  - Configurable timeout (default 3s) and retries (default 1)
- **MonitoringService (`app/Services/OLT/MonitoringService.php`):**
  - Orchestrates polling: system info, ONU status, traffic stats
  - Methods: `pollSystemInfo()`, `pollOnuStatus()`, `pollTrafficStats()`, `pollAll()`
  - Stores time-series data in `olt_snmp_stats` and `olt_traffic_stats` tables
  - Updates OLT device columns (cpu_usage, memory_usage, temperature, firmware_version, uptime_seconds, system_description)
  - Auto-cleans stats older than 7 days
- **PollOltOnuStatusJob:** Scheduler entry point — polls all active OLTs via MonitoringService with SNMP fallback to DB-only for non-SNMP devices; fiber cut detection (3+ ONUs offline on same port)
- **OLT Dashboard:** System info card + health metrics (CPU/memory/temperature progress bars) + port traffic table + signal quality distribution + recent alarms
- **OLT Forms:** Create/edit forms have `snmp_enabled` toggle + SNMP community/port fields; SNMP section shows when toggle is on OR connection_type is SNMP
- **Test Connection:** Uses SNMPClient for SNMP devices — returns system description, uptime, vendor ID; clear error messages for timeout/auth/unreachable

## Important Technical Notes
- **TenantContext::get()** is ONLY set in seeders/jobs — always use `auth()->user()->company_id` in controllers
- **jQuery loads AFTER @yield('content')** in admin layout — all jQuery scripts MUST go in `@push('scripts')`, NOT inside `@section('content')`
- **Database is PostgreSQL only** — many queries use PostgreSQL-specific features
- **View cache:** Always run `php artisan view:clear && php artisan view:cache` after blade changes
- **start.sh** auto-generates `.env` from Replit environment variables — no manual .env creation needed
- **`instrument_categories.has_serial`** — boolean (default true). When false, Product In skips serial fields and uses quantity
- **Product Out uses `$request->filled('bulk_out_id')`** (not `$request->has()`) to distinguish bulk vs serial mode
- **Non-serial Product Out creates new `in_use` row** — `$instrument->replicate()` with out quantity, original qty decremented
- **Client-to-product matching:** `instruments.assigned_to` and `instrument_out_logs.issued_to` store "ClientName (username)" string
- **`pppoe_username` column does NOT exist** in clients table — always use `username` field
- **`connection_status`** is the source of truth for online/offline (not `session_uptime`)
- **Client search widget:** Always use `@include('admin.partials.client-search', [...])` — NEVER use Select2
- **`instruments` table:** Uses `category` and `sub_category` columns (not `category_id`/`sub_category_id`)
- **Sidebar is hardcoded HTML** in `resources/views/layouts/admin.blade.php`
- **Name splitting:** No DB columns for first_name/last_name; backend merges in controllers
- **Installation Charge base entries:** `paid_by IS NULL` = charge record, `paid_by IS NOT NULL` = payment record
- **Application status "submitted"** displays as "Pending" via model accessor — DB value remains `submitted`
- **Blade @json() rule:** Never use PHP closures inside @json() — use @php block to prepare data first
- **Sale routes order:** Static routes before dynamic `{sale}` param routes in web.php
- **PostSetup.php** — as of Mar 12, 2026, ALL schema is permanently in migrations (300000, 300001). PostSetup is now DATA seeding + safety net only. New schema changes go in a NEW migration file, not PostSetup.
- **`clients` table has `client_id`** (not `client_code`) — use `client_id as client_code` in queries if needed
- **OLT SNMP form:** Username/password hidden for SNMP connections; single Community field; Port auto-used as SNMP port
- **Scheduler JS:** `var searchTimeout;` must be declared; `enablePPPoEUser()` method name must match; all functions in global scope
- **PPPoE secrets page:** Accessed via green key icon on MikroTik Devices list; shows router secrets vs billing comparison
- **`client` route alias** — `client` (singular) is an alias of `clients` route; NEVER reintroduce separate `client` routes
- **Payment forms** — ALL use `auth()->user()->allowedPaymentMethods()` — NEVER `PaymentMethod::where('is_active')`
- **`Company::hasMenuAccess($key)`** — checks exact key AND child-qualified keys in `allowed_menus` JSON. Any new menu key added must be registered in `Company::$menuStructure`
- **Employee `company_id`** — always set explicitly in `HrmController::storeEmployee()`. PostSetup fixes null values. `Employee::generateEmployeeId()` uses `withoutGlobalScopes()->where('company_id')` for per-company sequence.
- **Sidebar brand name** — comes from `$companyName` set by `AppServiceProvider::shareLogoSettings()` — uses `auth()->user()->company->name` for logged-in company users; uses SystemSetting `company_name` for unauthenticated/super admin
- **`payment_methods.code`** — compound unique `(code, company_id)` since migration `2026_03_12_200001`. NEVER insert with global unique assumption. Each company has its own `cash`, `bkash` etc.
- **`sms_templates.code`** — compound unique `(code, company_id)` since migration `2026_03_12_200000`. Each company gets its own copy of templates.
- **`seedCompanyDefaults($companyId)`** — called in `CompanyManagementController::store()` after company+admin creation. Also backfilled via `PostSetup::seedAllCompanyDefaults()` on every startup. Seeds 5 payment methods, 4 accounts, 3 income heads, 4 expense heads, 4 ticket categories, SMS templates, 4 departments, 4 designations per company.
- **New DB schema rule** — create a NEW migration file for any schema change. NEVER add schema to PostSetup. PostSetup is DATA-only as of March 12, 2026.

## MAC Reseller Billing System (GLN-inspired)
Per-client recharge tracking, monthly bill generation, ledger, and payment collection with commission.

### Database Tables
- `reseller_client_recharges` — per-client monthly recharge entries (reseller_id, client_id, bill_month/year, package_*, recharge_amount, start/end_date, days, status)
- `reseller_bill_payments` — admin payment receipts from resellers (amount, commission_amount, discount_amount, payment_method, received_by)
- Extended `resellers` table: over_due_limit, minimum_recharge_days, thana, area_name_en, area_name_bn, auto_recharge, recharge_day_type, single_recharge_day, flexible_min_days, terminate_hour, terminate_minute, serial_start_from, client_prefix, ppp_short_code, agent_id, referral_commission_percent, bandwidth_monthly_rate, mikrotik_device_id
- **ppp_short_code**: Admin sets per-reseller PPPoE username prefix; auto-prepended to username when reseller creates client
- **Reseller client codes**: Separated from main company — uses `client_prefix` + serial (e.g. "ABCD0001") via `Client::generateResellerClientId()`. Main company `generateClientId()` excludes reseller clients
- **Admin client list**: Excludes reseller clients (`whereNull('reseller_id')`); admin views reseller clients from Admin > Reseller section
- **Referral Partner (Agent) integration**: `resellers.agent_id` references `agents.id` (not users). Agent dropdown shows from `agents` table. When reseller bill payment is recorded, auto-creates `AgentCommission` (type=commission, purpose='Reseller Bill Payment') linked by `payment_id` for idempotency.
- **Referral commission priority**: Form manual input (if filled + numeric) > `reseller->referral_commission_percent` > `agent->default_commission`
- **Recharge day types**: `single` (fixed day), `multi` (any day, min days from reseller config), `flexible` (any day, custom `flexible_min_days` minimum enforced in service + modal HTML min attribute)
- **Flexible recharge**: `recharge_day_type = flexible` with `flexible_min_days` column (default 1, max 365)
- **Postpaid credit limit check**: Uses real-time calculation: `SUM(recharges) - SUM(curtailed_with_benefits) - SUM(payments)` instead of stored balance
- Extended `reseller_bills` table: total/active_clients, commission_rate/amount, discount_amount, opening/closing_balance, company_id
- **`bandwidth_monthly_rate`**: column on `resellers` table — fixed monthly ISP charge for bandwidth resellers

### MAC vs Bandwidth Reseller Separation
- **Two reseller types**: `mac` (MAC Binding — full portal) and `bandwidth` (bandwidth purchase — simple portal)
- **Route isolation**: `mac.reseller` middleware (`MacResellerOnly`) protects all MAC-only routes
- **Dashboard routing**: `ResellerDashboardController::index()` auto-redirects bandwidth resellers to `/reseller/bandwidth-dashboard`
- **Bandwidth portal**: `/reseller/bandwidth-dashboard` — shows bandwidth allocation (raw/yt/fb Mbps), monthly bills, wallet, account info; no client management
- **MAC-only routes** (inside `mac.reseller` middleware group): clients, zones, subzones, tjs, packages-manage, bills, recharge-client, curtail-client, collection-report, due-report, online-clients, all client CRUD/device operations
- **Shared routes** (both types): `/dashboard`, `/bandwidth-dashboard`, `/wallet`, `/profile`, `/api/live-stats`, wallet recharge
- **Admin forms**: Create/Edit reseller — JS toggles `#mac_billing_section` (hidden for bandwidth) and `#bandwidth_section` (hidden for MAC)
- **Billing**: `ResellerBillingService::generateMonthlyBill()` dispatches to `generateMacMonthlyBill()` or `generateBandwidthMonthlyBill()` based on type

### Reseller Client Management
- **Service Information Section:** GLN-style edit form with Package, Remaining Days, Per Day Charge (auto-calc), New Creditable Amount, Validity to Date (auto-calc), Username/IP, Password, Monthly Bill, Auto Renewal checkbox, Client Type, Billing Status, Expire Date (days), Joining Date, Effective To

### Credited & Recharge Transactions
- **View:** `admin/reseller/{reseller}/client-transactions` and `reseller/client-transactions`
- **Table columns:** UserName, Package, DailyRate, R.From Date, R.To Date, Days, CreditedAmount, TransactionType, CreditedOn, CreditedBy, Remarks
- **Transaction Types:** `recharge` (green badge, positive amount) and `curtailed_with_benefits` (red badge, negative amount)
- **Curtail Client:** Modal form to create negative/credit adjustment entries (deducts days × daily rate); for prepaid resellers, credits wallet back
- **DB columns added:** `transaction_type` (default 'recharge'), `daily_rate`, `credited_amount`, `remarks` on `reseller_client_recharges` table

### Billing Logic
- **Pro-rated day-wise billing:** `recharge_amount = base_price × days / 30` — cost scales with recharge duration
- **Expire-date extension:** Recharge extends from `max(today, current_expire_date)` — never shortens remaining validity
- **Prepaid:** Wallet balance checked (with row lock) before recharge, debited immediately in DB transaction
- **Postpaid:** Recharges recorded as bills; payments credit wallet and reduce due
- **Status model:** Uses 'suspended' status (DB enum: active/inactive/suspended). UI shows "Terminated" label for suspended resellers.

### MikroTik Integration
- **Client creation:** When reseller adds a client, system auto-creates PPP secret/hotspot/queue on the reseller's assigned MikroTik router via `SimpleMikroTikService::createClientByType()`
- **Reactivation on recharge:** When expired/inactive client is recharged, system auto-enables on MikroTik via `enableClientByType()`
- **Router scoping:** Resellers can ONLY use their assigned `mikrotik_device_id` — no global fallback
- **Non-blocking:** MikroTik failures don't prevent client creation or recharge — errors are logged
- **Client delete → MikroTik secret deleted:** When reseller deletes a client, the MikroTik secret/user/queue is fully removed
- **Client restore → MikroTik secret re-created:** When reseller restores a deleted client, `createClientByType()` re-adds the secret

## Recent Architecture Changes (2026-03-20)

### system_settings Multi-Tenancy Fix
**Problem**: `system_settings` table had `UNIQUE(key)` constraint (single-column), making it impossible to have per-company settings since all companies share the same key names.

**Fix applied**:
- Migration `2026_03_20_010000_fix_system_settings_unique_constraint.php`:
  - Drops `system_settings_key_unique` (single-column)
  - Converts all `company_id=NULL` rows to `company_id=1`
  - Adds `system_settings_key_company_unique` (composite `UNIQUE(key, company_id)`)
- `SystemSetting::set()` already uses TenantAware + company_id resolution — now works correctly
- `SystemSetting::get()` simplified: no more NULL-company_id fallback (all rows have company_id now)
- `RoleServiceProvider::ensureSystemSettingsExist()` now uses composite key `['key'=>..., 'company_id'=>1]` for `updateOrInsert`; seeds 9 defaults including `client_portal_change_package`
- `PostSetup::seedAllCompanyDefaults()` now seeds per company: system_settings (9 keys), automation_settings, SMS templates (BILL_GEN/PAY_RECV/ACC_ACT/ACC_DEACT/DUE_REM codes), payment methods with uppercase codes (CASH/BKASH/NAGAD/ROCKET/BANK)
